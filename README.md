# Integration Test（IT）方針ガイドライン

## 1. 目的

Integration Testの目的は以下の通り：

- 外部(Grpc/Rest)機能呼び出しの振る舞いが正しいことの検証
- APIとしてのIFが（I/O）が正しいことの保証
- トランザクションやインフラ依存の挙動確認

---

## 2. 基本方針

### ❌ やらないこと
- ビジネスロジックの分岐網羅
- 条件分岐（if / switch）の全パターン網羅検証
- データバリエーションの網羅

👉 上記はすべて`UnitTest`の責務とする

---

### ✅ やること

#### 1. 外部から観測可能な「振る舞い」の検証

##### 外部(Grpc/Rest)機能呼び出し
- 呼び出しが行われることの検証
- 呼び出し時のリクエスト内容の検証

##### DB更新
- 更新結果（最終状態）の検証
  - 更新項目のみ
  - 想定外の更新が実施されていないかは`更新項目数`で検証とする
- トランザクションを考慮した整合性の検証

##### リクエスト
- 認証に関する検証が実施されていること

##### レスポンス
- レスポンス内容（通常/エラー）
- HTTP/gRPCステータス
- エラーコード

##### ログ
- 機密情報が出力されていないことを検証していること

※予約語については自動で検証される

---

#### 2. 代表的な正常系・異常系の確認

- 正常系：1ケース
- 業務エラー：エラー種別ごとに1ケース
- システムエラー：1〜2ケース

※上記はシンプルなAPIの例であるため実際はAPIの難易度により異なる

---

#### 3. インフラ依存の挙動検証

- Transaction（Commit / Rollback）
- DB制約違反

---

#### 4. 冪等性の検証

- 同一リクエストで二重実行されないこと
- 二重実行時の振る舞いが想定通りであること
- データ不整合時に不整合が解消される構成となっていること

---

## 3. 判断基準

以下の問いでテスト種別を決定する：

### Q1. このテストはロジックの正しさを検証しているか？
→ YES：Unit Testで実施

---

### Q2. このテストは外部から見た振る舞いを検証しているか？
→ YES：Integration Testで実施

---

### Q3. この不具合はUnit Testで検知できるか？
→ YES：Integration Testでは不要
